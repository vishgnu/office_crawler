## Should

### CR7L-01 Toast lane protects a quest line only against lines that come after it; the level-up that the same reward causes comes before it
`src/core/systems/quests.js:82-86` (arc: `giveGold`, `gainXp`, then `emit quest.completed`) and `:360-365` (`handInQuest`: `gainXp`, then `emit quest.completed`); `src/game.js:336-362` (`showToast`, `game.toast`); `src/ui/panels.js:357-365` (`syncToast`).
Events reach the bus in emit order. A reward that levels the hero up emits `levelup` first, then `quest.completed`. `levelup` is a passive line, but no lane is held yet, so it shows at once (`showToast`, with an `emitChange()` that writes the live region), and the quest line replaces it in the same dispatch. The same happens for `floorEnter` followed by `quest.step`/`quest.completed` when an arc finishes on entering a floor (the tap runs inside `emit(floorEnter)`). Result: the level-up line and the floor name are never on screen, and the live region (`role=status`, `aria-live=polite`) is rewritten twice in one task (`textContent = ""; textContent = text`), so a screen reader will normally announce only the last text. The ADV-R7-02 fix covers the one order (`kill` -> `quest.step` -> `levelup`) the e2e uses. e2e `adv-r7.mjs:455` asserts `live.textContent` after the fact, which cannot see an announcement that was overwritten.
Fix: do not show the first message of a dispatch immediately. In `dispatchFrom` (game.js:201) collect the lines of one dispatch, order them (quest lines first or in event order) and feed them to the queue so the second and later ones wait their turn (the existing queue and 4 s hold are enough); or emit `quest.completed` before `gainXp` in the two core places (hash-neutral: quest events are stripped in the golden proof, but check the quest-on goldens). Add a unit test on the shell function with the sequence `levelup, quest.completed` and `floorEnter, quest.completed`, asserting both texts are shown or announced in order.

### CR7L-02 A direct toast replaces a held quest line and empties the waiting list
`src/game.js:337-343` (`else tq.q.length = 0`), `:348-362`; callers `game.js:107-109` (`pointsHint`), `panels.js:501,611-620` (refusals, hints).
`showToast` for a non-quest line clears `tq.q` and the timer. Every "direct feedback" call (a refusal, a hint, the points hint at the first level-up with unspent points) therefore cuts a quest line short (the AC says at least `toastMs`) and silently drops every passive and quest line that was waiting. Also in `game.toast`: `tq.q.filter((w) => w.kind !== n.kind ...)` replaces a waiting line of the same kind, so two different potion lines in a burst keep only the last; `tq.q.length < 4` drops the fifth without a trace. For a screen-reader user these are lost messages (the live region only ever gets what is shown).
Concrete order: `levelup` is handled by the toast handler (queued behind a held quest line) before `pointsHint` (a later `bus.on("levelup")`) shows `T.pointsHint` directly, which replaces the quest line and wipes the queue holding the level-up line.
Fix: direct lines should queue behind a held quest line like passive ones (priority over passive, not over a quest line), `showToast` must not clear the queue, and a dropped or merged line should still be written to the live region (the region can take them one after the other even when the visual toast shows only the latest). Test: hold a quest line, send a direct line and a passive line, assert the order and that nothing is dropped.

### CR7L-03 Nameplates of the last frame are replayed on the title backdrop after leaving a run
`src/game.js:496-501` (`fx.plateDraw = labels.draw` only inside `if (game.core)`), `src/render/fx.js:352` (`if (fx.plateDraw) fx.plateDraw(g)` for any `core`), `src/render/labels.js:200` (`draw` replays the module-level `placed` and `pips` of the last `place`).
VFIX-R7 moved the plate drawing from `game.js` into `fx.draw`. Before, `labels.draw(g)` ran only when `game.core` existed. `fx.draw` runs for the title backdrop too (`drawWorld` sets `fx.core` to `game.backdrop`), `plateDraw` is never cleared, and `labels.place` is not called without a run, so after "Back to title" (or any `toTitle`) the last frame's name plates, hp bars, crowns and pips are drawn over the backdrop Lobby for as long as the title shows. Not reproduced in a browser (no browser here); established by reading the three call sites. `resetRender`/`fx.reset` do not touch it.
Fix: in the render function set `fx.plateDraw = game.core ? labels.draw : null` (the else branch), and add a unit test with a stub canvas that counts draw calls after `toTitle`.

### CR7L-04 The far-hold rule makes the hero stand for seconds in plain corridors, and its tests cannot see it
`src/core/systems/intent.js:289-291`, `src/core/config.js:26` (`holdFarTicks: 480`), `test/chase-orbit.test.js:30-33,49-62`.
I measured (probe on the `9174926` extract, a 44-wide room with a wall that blocks the line, hero and chaser 40 tiles apart by the walk, damage off, 3 monster kinds, rule on vs `holdFarTicks = 0`): longest stand-still 243, 227 and 251 ticks with the rule against 36, 24 and 60 without; contact after 741, 589 and 1033 ticks against 656, 493 and 984. So an explicit attack click on a chasing monster without a line to it freezes the hero for about 4 s (the rule allows 8 s), and the fight starts 50 to 100 ticks later than without the rule, in a geometry that is not an orbit at all. The tests only assert "contact within 400 ticks" on the staged ring and "contact within 3000 ticks" on 600 random maps, so a slow, frozen hero passes. The hold also ignores `slowT`/`slowMag` (the arrival estimate uses the base speed) and the monster's real target (an ally decoy that stands within 2 tiles of the hero holds the hero too).
Fix: bound the wait by what orbiting needs: hold only while the chaser's remaining path is at most about one ring half (for example `m.path.length <= 2 * holdRadius + 8`) or hold for at most about 120 ticks, then walk; and assert in `chase-orbit.test.js` a maximum stand time (for example 250 ticks) and an upper bound on the contact time of the staged ring (it is about 100-200 ticks). Keep the "rule off orbits" test; it is good.

### CR7L-05 `withLegacyBalance` is honest for floors and monsters but does not restore the boss numbers, and the proof only reaches floor 3
`test/balance-legacy.js:11-24` against `src/core/config.js:159` (`boss.hpMult 3 -> 2.5`, `damageMult 0.7 -> 0.62`, item 6 of `R7-balance.md`).
What I verified by running it (two checkouts in the scratchpad: `0934a57` and `9174926`): under the helper, `generateFloor(seed, d).spawns` for seeds 1-60 and floors 1-8 hash to `2ede4bf3e002ac56aacf68d86ef3b2c491e634a9` in both (equal; without the helper they differ), and `monsterStats` for all 8 monsters plus the boss on depths 1-9 hash equally (`2778347640` both). So the helper does restore every lever it lists and cannot hide drift in them; and it cannot mask unlisted drift either (that shows as a different hash). Two gaps:
1. The boss multipliers are not restored (the boss stats differ from `0934a57` under the helper; I included them in a first hash and it differed). No recorded run fights the boss, so no golden notices, but `R7-balance.md` says the proof shows "nothing else moved"; it shows that for floors 1-3 (run-a stays on floor 1, run-b/run-c reach floor 3) and not for the boss, the vending machine on floors 4+, or the population of floors 4-8. My generator check closes this for floors 1-8 once, by hand; nothing in the suite keeps it closed.
2. The helper is synchronous: if `fn` returns a promise the `finally` restores before it runs. Nobody does that today.
Fix: add `config.boss.hpMult/damageMult` to the helper, and add a test that, under the helper, hashes `generateFloor` spawns (seeds 1-60, floors 1-8) and `monsterStats` (all types, depths 1-9) against the two values above (recorded from `0934a57`, reproduced by me). That turns a one-off check into a permanent proof for floors 4-8. Throw in the helper when `fn` returns a thenable.

### CR7L-06 Quest gear rewards are almost always the lowest-tier base (the CR7-06 fix over-corrected)
`src/core/systems/quests.js:321,329-344` (`reqCost`, `rewardOf` takes the candidate that asks the least of its wearer).
`rewardOf` rolls `rewardRerolls` (8) candidates at the quest's fixed item level and pays the one with the smallest `reqCost`. I tallied 300 seeds (facilities-manager) with the real function: sq2 gives a level-1 base in every case (wrist-brace 95, sneakers 73, visor-cap 64, cardigan 61; 85 to 90 % magic), sq3 always a level-1 weapon base (pipe-wrench 77, usb-staff 76, letter-opener 78, ruler-rapier 69), sq5 a level-1 belt, ring or lanyard in 288 of 300 cases. The reward for a floor 4 elite and a floor 6 consultant hunt is the entry-level base of the slot (with magic affixes at the quest item level). That removes the fishing exploit (good, CR7-06 closed) but also removes the reward's value curve, and `rewardRerolls` now means "pick the weakest".
Fix: keep the candidates seed-pure but choose by a seed-pure rule that does not favour the weakest base: for example the highest item level or tier among candidates whose `reqs.level` is at most a reference level derived from `gearFloor` (not the hero), or the first candidate whose requirement is at most that reference. Decide the intended reward quality with the customer (it is a balance dial, not a bug); at least rename the config key and say so in the ADR.

## Checked without a finding

- **Arc derivation** (`questview.js:11-30`, `content/quests.js:5-38,133-135`): the suffix-OR over ten steps gives a monotone, total derivation; `mainState` partitions into completed, one active, rest locked for every milestone combination (the exhaustive test in `quests-arcs.test.js` covers it). Step predicates are data. Arcs 2 and 3 have no stored state, so there is nothing to desync.
- **Pay-once** (`quests.js:74-95`): payment keys on the derived state before and after one reducer call, so a repeated event, a save/load (`loadSave` sets the block without an event; its `enterFloor` cannot raise `m.depth` because the schema ties `m.depth` to `deepestDepth` and play raises both together), a catch-up over two arcs (paid in order, once each) and a migration (no event) pay nothing twice. Re-entrancy: payment emits `levelup` etc., which the tap ignores unless it is a `floorEnter`/`stairsUnlocked`/`bossDefeated`/`keepPlaying`. A migrated v4 hero at depth >= 3 never receives the arc 1 reward (documented, intended).
- **Save v5 and schema** (`save/format.js:198-222`, `migrate.js:89-101`, `slots.js`): `MIGRATIONS[4]` is pure, returns v5 input unchanged and never throws on malformed input; the pin remap uses the derived active arc. I looked for false rejections along every new rule: the `deepestDepth` floor for partial kill progress (kills happen only on kill floors, so deepest is at least the floor), the shared kill counter (`stats.kills` is incremented for every kill and never reset; only finished quests are summed, so a partial quest cannot cause a rejection), the pin rule (`repin` keeps the pin on the derived active arc when an arc completes, a pinned side quest stays valid until completed, the alias `main` is stored as the arc id) and the item and elite floors. 1500 random sequences of the quest cheats, kills, teleports, pins and ticks saved and loaded with 0 rejections; the v4 fixtures migrate. The index upgrade keeps unrebuildable entries without quest fields (no card line, no crash).
- **Kill top-up** (`quests.js:229-282`): deterministic (own stream `purpose 6`, no `state.rng`, no id dependence except the monster ids of the extras, which exist only for a player with an active kill quest); idempotent across re-entry because the need falls as the progress rises and the extras are not in `floor.spawns`; counts only own-kind, non-summoned, living monsters; a run that never accepts is untouched (placement returns before drawing). The "alive" count of the other kill floors uses `generateFloor` for floors not yet visited (pure), at the price of a floor generation per entry of the last kill floor while the quest is active (a few ms, once per entry).
- **Own-property quest ids** (`questDef`, `Object.hasOwn`): used by every input and cheat entry (`questAccept`, `questPin`, `questHandIn`, `handInQuest`, `setQuestStep`, `completeQuest`); the remaining bare `quests[id]` reads take ids from content lists or from a validated save (`pinned`), checked by grep.
- **Injection**: journal, quest dialog, tracker, slot card and toast all use `esc()`, `textContent` or `el(..., text)`; ids that reach `data-*`/`aria-label` are escaped and come from content; `CSS.escape` is used for the focus restore selector; quest and reward strings are core content, the only player-controlled string (the character name) is not placed into quest markup; the slot index values (`mainStep`, `sidesDone`) go through `String()`/clamping and `textContent`.
- **Render changes**: new work per frame is small and allocation-free (`lt.r2`/`lt.r3` reused, `onChamp` is an early-out scan of the visible bodies, the plate search grew from 5 to 9 tries inside bounded loops, the NPC marker lift loops at most 3 x plates). `game.reduced()` reads a cached `MediaQueryList`. `syncToastDup` forces a layout read only when a `.nq-warn` alert exists. The OS reduced-motion preference is honoured in the world render, the hurt flash, shake, toast CSS and the character select.
- **Duplicate-hiding** (`panels.js:349-356`, `.toast.dup{visibility:hidden}`): the toast text is written to the live region before it is hidden, so a hidden duplicate does not lose its announcement (the pill and the alert carry the visible text). No finding on this rule itself; the lost messages are CR7L-01/02.
- **Bot**: `bot/quests.js` still uses public inputs only; the Exit trip falls back to the stairs; the watchdog change (drop the order of a written-off monster) is bounded by `mem.skip` and re-enabled when the monster attacks.
- **Closed earlier findings, verified in the code**: CR7-01 (sq1 revive: `reviveKills`), CR7-02 (quest entries outside the log window), CR7-03 (`holdMaxTicks` test, `retargetEvery` throttle, `standT` reset), CR7-04 (lane, subject to CR7L-01/02), CR7-05 (`rewardSummary` is the single source: the journal and dialog read it), CR7-06 (reward independent of hero stats: closed, but see CR7L-06), CR7-08, CR7-14.
