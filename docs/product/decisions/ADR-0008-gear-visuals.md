# ADR-0008 Gear visuals: the hero's figure follows the equipped gear

Date: 2026-10-15. Status: proposed (architect; the customer asked for the feature in the seventh briefing, `../00-brief.md`; no open customer question blocks it). Implements R-260..R-262 (`../30-spec/13-gear-visuals.md`), work packages R8-0.1..R8-0.3 (`../50-plan.md`). Builds on ADR-0004 (atlas, budgets), ADR-0006 (slot index), art direction C-dark (`variants/art-direction/decision.md`), `docs/reviews/R6-perf.md` and `R7-stutter.md`.

## Context

- Today the hero sprite ignores equipment. `src/render/styles/vector/heroes.js` draws each class (`hero(g, id, o)`, 8 facings, anims idle 4 / walk 6 / attack 4 / death 4 / cast 4 = 22 frames x 8 = 176 frames a class) with a fixed outfit and a fixed prop (FM wrench, SR stapler/cards, IT laptop). Frames are lazy atlas entries (`plr:<class>:<anim>:<dir>:<frame>`, 104 x 96 logical px, rim ring baked in) filled on first `atlas.get` and pre-drawn by `warmFrames` (`world.js`, 1.5 ms a frame, hero first).
- Atlas facts: eager build is 0.4-0.5 s (R6-perf); the 4.78 s of the R5 acceptance was the old eager build, before monster and hero frames became lazy. The 5 s load budget (NFR-P02, ADR-0004 point 5) therefore must not grow: gear adds nothing to the eager build. A lazy hero frame costs about 1.1 ms (figure plus rim bake). fps50 median must stay >= 48 (PERF-R6 target; last measured median 46.8 under load 3-5, the machine is the limit, so the rule here is "no measurable change against the pre-R8 bench on the same machine, and the absolute gate of the bench"). R7-2 rule: after a floor load frame p99 <= 33 ms; `warmAhead` waits 240 frames after each floor change; nothing new may draw in that window.
- Item data: bases in `core/content/items.js` (30 gear bases; `slot`, `twoHanded`); a rolled item carries `base` (base id), `rarity` (`normal|magic|rare|unique`), `slot`, `unique` (unique id, only on uniques), `twoHanded`. Equipment is `state.equipment[slotKey]` (item object or null; replaced, never mutated in place).
- Visible slots (brief, seventh): head, body, hands, feet, weapon, offhand. Belt, ring1, ring2, amulet are not drawn.
- Layering rule N5: `ui/` may not import `render/`; the shell hands over `figures` (`ui/figureHost.js`).

## Decision

### 1. Drawing: vector parts per base category, painted inside the hero painter
1. **Which field selects the part:** `item.base` (the base id) looked up in a render-side table `LOOK_BY_BASE` in new `src/render/gearlooks.js` (`base id -> category`). Not per item, not per affix, not per name. **No change to `core/content/items.js`** (so CORE-R8-1, which may touch it, cannot collide); a Node test fails when a base in `content.bases` of kind `gear` and a visible slot has no entry.
2. **Categories (21, fixed list in `gearlooks.js`):** weapon 5: `blade` (ruler-rapier, letter-opener, keyboard-sword), `blunt` (pipe-wrench, stapler-mace, hole-punch-hammer), `staff` (usb-staff), `pole` (mop-halberd, two-handed), `heavy` (extinguisher-club, two-handed); offhand 3: `board` (clipboard-shield), `binder` (binder-buckler), `tray` (serving-tray-aegis); head 3: `cap` (visor-cap), `helmet` (hard-hat), `headset` (headset); body 4: `knit` (cardigan), `jacket` (blazer), `vest` (hi-vis-vest), `suit` (pinstripe-suit); hands 3: `brace` (wrist-brace), `gloves` (rubber-gloves), `mitts` (typing-mitts); feet 3: `sneaker` (sneakers), `loafer` (loafers), `boot` (steel-toe-boots). New bases join an existing category or a new one with one table line.
3. **Class variation without class x category art:** each part painter is one function `(g, slot, category, tier, A)` where `A` is the **anchor set** the class painter already computes (head centre and radius, shoulder/hip line and torso half width, hand points, feet points and size, facing vector, `front`). Classes differ in the anchors (FM wide, SR slim, IT hunched), not in separate drawings. 21 painters, not 63.
4. **Rarity tier on the part:** `tier` = 0 normal, 1 magic, 2 rare, 3 unique, painted by one shared helper `trim(g, path, tier)` so every category reads the same way and never by colour alone (NFR-A03): normal = ink outline only; magic = one sky-blue (#56B4E9) edge line; rare = double yellow (#F0E442) edge plus two studs; unique = vermillion (#D55E00) edge plus a small bright diamond/spark accent and a thin light-orange (#E69F00 family) outer rim on the part. Okabe-Ito colours already live in `palette.js` (rarity block); the helper reads them from there. All uniques share the one unique accent (no per-unique art), so the signature set stays small.
5. **Layer order is the painter's, per facing:** the class painter calls `gearHook(g, "legs"|"feet"|"torso"|"head"|"hands"|"weaponBack"|"weaponFront"|"offhand", ...)` at the points where it already draws legs, shoes, torso, head, arms and props, so back-facing arms, behind-the-body weapons and the body over the off-hand stay correct for all 8 facings and every anim (including `death` rotation and `cast`). A part is therefore **not a separate bitmap**: it is vector code executed in the same draw as the body.
6. **Empty slot = today's look.** With nothing equipped in the six slots the painter runs with no hooks and the output is the existing sprite pixel for pixel (class outfit, class prop). The class prop is the default of the weapon slot (FM wrench, SR stapler/card fan) or the off-hand slot (IT laptop); an equipped item in that slot replaces the prop, an empty slot keeps it. `death` frames draw gear like all others.
7. **Two-handed:** `item.twoHanded` (or category `pole`/`heavy`) uses the two-hand pose in the weapon hook and the off-hand hook draws nothing (core already blocks an off-hand with a two-handed weapon).
8. **Fallback for unknown bases:** category = `LOOK_BY_BASE[item.base]`, else the plain default of the item's slot (`cap`, `knit`, `brace`, `sneaker`, `blade`, `board`; a two-handed unknown weapon uses `pole`), else (unknown or invisible slot, null, malformed object) nothing is drawn for that slot. Unknown rarity counts as normal. A part painter that throws is caught once per signature; that slot is drawn empty, `perf().gearFallbacks` counts it and the frame still renders. No path throws into the frame loop or the atlas build.

### 2. Composition and cache: one baked sprite per frame, cache keyed by equipment signature
- **Rejected: runtime layer compositing per frame** (body sprite plus 6 part bitmaps blitted each frame): needs part bitmaps for every category x class x 176 frames, breaks the rim ring (the rim must wrap the whole figure) and costs 7 blits a frame for the hero alone, with 50 monsters in the budget.
- **Rejected: pre-baking all combinations**: 21 categories x 4 tiers over 6 slots is millions of signatures; even one signature is 176 frames (about 0.2 s). Out of the 5 s budget by orders of magnitude.
- **Chosen:** the **signature** `sig(equipment)` is a short string over the six visible slots in fixed order, each `-` (empty) or `<categoryCode><tier>` (for example `b2|-|k0|-|s1|-`; two-handed weapons add `2`). Pure function in `gearlooks.js` (`gearSignature(equipment)`), no RNG, no allocation per frame (it is recomputed only on change, see 4). The world keeps **one cache per atlas**: `Map<signature, table>`, where `table` has the same shape as `heroFigs` (`anim -> dir -> frame -> entry`). An entry is built **lazily on first use** by running the class painter with the gear hooks and the same `figureWithRim` bake as atlas hero frames, into a fresh offscreen canvas of the same size and anchor as the atlas entry (so `blit`, `flash`, `shade`, `outline` work unchanged). The all-empty signature `-|-|-|-|-|-` maps to the existing atlas keys (no copy).
- Per-frame cost at runtime: identical to today (one lookup, one blit). First sight of a frame of a new signature costs one lazy draw (about 1.1-4 ms, the same as any lazy hero frame today); the hero shows one frame per rendered frame, so at most 1 such draw per frame by construction.

### 3. Budget (numbers the tests enforce)
| Item | Budget |
|---|---|
| Eager atlas build (`perf().atlasMs`) | unchanged: no gear sprite is drawn at boot; gate stays `< 5000 ms`, expected 0.4-0.7 s |
| Gear cache memory | hard cap **32 MB** of pixel data (`width x height x 4` per entry, scale taken from the atlas); at scale 1 about 40 KB a frame (800 frames), at scale 2 about 160 KB (200 frames). LRU by last-use frame; the **current signature's frames are never evicted while in the last 120 frames**; the previous signature's frames go first |
| Residency | the current signature plus at most one previous (undo, swap back) with the cap above; no per-frame canvas allocation (entries are built on a cache miss only, canvases then live in the cache) |
| Warm after a change | `warmGear(atlas, core, 0.7 ms)`: idle and walk, 8 facings (80 frames, about 90 ms of work, spread over about 2 s at 0.7 ms a frame), then attack, cast, death on demand only. Starts the frame after the change |
| Floor-entry rule (R7-2) | a floor change does **not** change the signature, so it costs the gear cache nothing. No gear warm runs in the 240 frames after a floor change (same pause as `warmAhead`), except an on-demand draw of the frame being shown. Gate stays: frame p99 after floor load <= 33 ms; `lazy` draws inside the measured window stay 0 |
| Entering the game | `warmGear` runs unbudgeted for idle and walk (80 frames, about 90 ms) behind the existing class-select to game transition and Continue, so frame 1 is warm |
| fps50 | median of 5 bench runs >= 48 on the CI reference runner where the pre-R8 bench is >= 48, and on any machine not more than 1 fps below the pre-R8 median measured in the same session. 50 monsters, hero fully geared in all six slots, unique tier |
| UI figure draws | live, uncached except the bust cache of section 5; at most 1 live figure draw per UI frame budgeted at 3 ms |

### 4. Invalidation
- The renderer compares the **six item references** (`state.equipment.head`, `body`, `hands`, `feet`, `weapon`, `offhand`) with the last seen ones once per frame: 6 identity compares, no allocation. Equipment slots hold replaced objects (equip, unequip, swap, load, new game, death penalty all assign), so a changed reference is the whole trigger. On a change only: recompute the signature string; if it differs, switch `F.hfigs` to that signature's table and start `warmGear`; if it is equal (same category and tier, another item), nothing is rebuilt.
- Load game, new game, class change and respawn go through the same compare. The cache key includes the class (`<class>/<sig>`), so a class change never reuses the wrong body.
- A style or scale change (atlas rebuild) drops the whole gear cache with the atlas (it is a `WeakMap` keyed by atlas, like `figTables`).
- Stale frames are never drawn: the table swap is atomic within a frame.

### 5. Shared with the UI (Employee File, select, busts)
- `render/figure.js` `drawFigure(canvas, figureKey, { anim, t, dir, look })` gets one optional `look`: a signature string (or an equipment object, which `figure.js` converts with `gearSignature`). Absent or `-|-|-|-|-|-` gives today's drawing, byte for byte. It paints live with the same class painter and gear hooks (no atlas, the UI never touches the world cache), so **the parts are the same code in game and UI**; only the cache differs.
- `ui/figureHost.js` `provideFigures` gains `look: (equipment) => signature`, wired in `main.js`, so `ui/` stays free of `render/` imports. The UI passes either a state equipment object or a stored signature.
- Employee File (`ui/panels.js`, `canvas[data-bust]` at the head of the sheet): `paintBust(canvas, classId, look)`; `bustSource` is cached per `class + look` (LRU of 8 canvases of 480 x 600, about 9 MB at most), repainted when the panel's existing change signature (equipment ids) changes.
- Slot busts (`ui/slots.js`): saved characters are not loaded, so the slot index entry stores the look. `src/save/slots.js` adds an optional field `look` (the signature string, max 40 chars, validated by regex; computed from the saved `equipment` at save time by the same pure `gearSignature`, imported from the pure, DOM-free `render/gearlooks.js`; if the layering test objects it moves to `src/core/content/`, see R8-0.3 risk). An entry without `look` is drawn bare (today's bust) and is rewritten at the next save of that slot; no index rebuild is needed. No save version change, no state change.
- Character select class cards (new character, nothing worn): show the class's starting kit if `wearStartKit` equips a weapon (the shell passes the kit's weapon base), else bare. This is a one-line data call, covered by AC-R-260-6.

### 6. Determinism and golden
Render only. Nothing in `src/core`, `src/save` state, or `bot/` changes; gear painters never call `Math.random` or core RNG (painters are pure functions of the signature and pose); the art RNG is not used. State hashes, `run-a.json`, `run-class.json`, balance goldens and save formats are unchanged (AC-R-262-1 asserts it with the recorded runs, rendering on and off). Pixels: same signature, class, anim, dir, frame gives identical pixels within one engine (AC-R-262-2).

## Consequences
- Memory plus about 32 MB worst case on top of the 4 pages of the atlas; scale 2 holds fewer frames, so the second signature may be partly evicted (it rebuilds on demand, 1 draw a frame).
- The hero painters in `heroes.js` (296 lines) gain hook calls; the S1 `clerk` hero (`characters.js` `human`) is not a playable class any more and gets none (its drawing is unchanged).
- Part art is the bulk of the work (R8-0.2); the render core (R8-0.1) is shippable with a stub painter per slot, so the cache, budget and invalidation are testable first.
- A new base without a table entry still renders (slot default) and fails the data test, so it cannot ship unnoticed.
- Overlap with CORE-R8-1 (bag-full rewards, first pack, entry safety, potions): none. Gear visuals only read `state.equipment` and write nothing; the files differ (`src/core/**`, `bot/**` there; `src/render/**`, `src/ui/**`, `src/save/slots.js` here). Shared files to watch: `main.js` (one line in R8-0.3) and `testhook/index.js` (read-only `perf()` fields). If CORE-R8-1 gives bought or rewarded gear a new field, gear visuals do not read it.

## Options considered
| Option | Verdict |
|---|---|
| Per-item art (one part per base or per unique) | Rejected: 30 bases x 3 classes x 4 tiers, no budget; categories carry the look, tier carries rarity |
| Runtime layered blitting of part bitmaps | Rejected: rim ring, anchor drift per frame, 7 blits a frame, part bitmaps per frame index |
| Pre-bake all signatures at boot | Rejected: breaks the 5 s load budget |
| Bake only on equip, whole 176 frames at once | Rejected: about 0.2 s block in one frame; lazy plus 0.7 ms warm is smooth |
| Field `look` on every base in `items.js` | Rejected for now: touches core content that CORE-R8-1 may edit; the render table plus a data test is equivalent |
| Share the world cache with UI busts | Rejected: UI is live-painted at 1 to 4 figures and has no atlas; coupling would break layering N5 |
